## 2. Detailed Permission Justifications

### High-Risk Permissions (Play Protect Sensitive)

#### BIND_NOTIFICATION_LISTENER_SERVICE
- **Feature:** Communication AI (features/communication)
- **Purpose:** The AI assistant needs to read notifications from other apps to provide intelligent summaries, reminders, and contextual awareness. For example, summarizing a chain of messages or alerting the user to important notifications.
- **Play Protect Impact:** HIGH - This is one of the most sensitive permissions as it provides access to all notification content from all apps.
- **Mitigation:** Only used when user explicitly enables the notification access feature. Runtime permission dialog clearly explains the scope.

#### READ_SMS
- **Feature:** Communication AI (features/communication)
- **Purpose:** AI-powered message analysis - summarizing conversations, extracting action items (appointments, addresses, codes), and providing intelligent reply suggestions.
- **Play Protect Impact:** HIGH - SMS access is heavily scrutinized by Google. Apps requesting this without being the default SMS handler face additional review.
- **Mitigation:** Read-only access. No sending capability. Feature is opt-in with clear user disclosure.

#### READ_CALL_LOG
- **Feature:** Communication AI (features/communication)
- **Purpose:** Provides the AI with call history context to identify communication patterns, missed calls requiring attention, and integration with contact-based intelligence.
- **Play Protect Impact:** HIGH - Call log access is restricted and requires Play Store declaration review.
- **Mitigation:** Read-only access. No call initiation. Used only for contextual AI features.

#### READ_CONTACTS
- **Feature:** Communication AI (features/communication)
- **Purpose:** Contact-aware AI responses - identifying who is calling/messaging, personalizing responses based on relationship context, and enabling natural language references to contacts.
- **Play Protect Impact:** MEDIUM - Common permission but contributes to risk score when combined with SMS/call log access.
- **Mitigation:** Read-only access. Contact data processed on-device where possible.

#### SYSTEM_ALERT_WINDOW
- **Feature:** Overlay Assistant (features/overlay)
- **Purpose:** Core UX paradigm - the AI assistant appears as a floating overlay bubble that can be accessed from any screen without switching apps. This is the primary interaction model for quick AI queries.
- **Play Protect Impact:** MEDIUM - Overlay permission is monitored but widely used by legitimate apps (Facebook Messenger, screen recorders, etc.).
- **Mitigation:** User must explicitly grant overlay permission through system settings. Overlay is dismissible and respects system restrictions.

#### CAMERA
- **Feature:** Vision (features/camera)
- **Purpose:** AI-powered visual analysis - document scanning, object identification, scene understanding, visual question answering.
- **Play Protect Impact:** LOW-MEDIUM - Camera is a common permission for many app categories.
- **Mitigation:** Only active during explicit camera sessions initiated by user. No background capture.

#### RECORD_AUDIO
- **Feature:** Voice Assistant (features/voice)
- **Purpose:** Core voice interaction - capturing user speech for AI processing, voice commands, dictation.
- **Play Protect Impact:** LOW-MEDIUM - Expected for assistant-type applications.
- **Mitigation:** Only records during active voice sessions. Foreground service notification visible when active. User-initiated.

## 3. Play Protect Analysis

### What Triggers Play Protect Warnings

Google Play Protect uses a machine learning model that evaluates multiple risk signals:

1. **Certificate Trust Level**
   - Debug certificates (CN=Android Debug, O=Android, C=US) have near-zero trust
   - Unknown production certificates have low trust until reputation is established
   - Certificates enrolled in Play App Signing have the highest trust

2. **Distribution Channel**
   - Play Store distribution: highest trust (pre-scanned by Google)
   - Enterprise sideload: medium trust (managed devices)
   - Direct APK sideload: lowest trust (no Google verification)

3. **Permission Risk Score**
   - Each dangerous permission contributes to a cumulative risk score
   - Certain combinations (SMS + Call Log + Contacts + Notification Listener) significantly elevate risk
   - The score alone rarely blocks installation but compounds other factors

4. **App Behavior Signals**
   - New/unknown apps have no behavioral history
   - Apps with similar permission profiles to known malware trigger higher scrutiny
   - Code patterns (obfuscation, dynamic loading, native code) can increase suspicion

### Why Sona AI Was Blocked

The block was triggered by the combination of:

| Factor | Weight | Status |
|---|---|---|
| Debug certificate signing | **PRIMARY** | Fixed - pipeline now uses production signing |
| Sideload distribution (no Play Store) | **PRIMARY** | Cannot be fixed without Play Store distribution |
| Sensitive permission combination | **SECONDARY** | Legitimate - cannot remove without losing features |
| No app reputation history | **SECONDARY** | Will improve after Play Store listing |

### What Can Be Fixed

- **Debug certificate** - FIXED. Release pipeline now uses dedicated production signing key.
- **Certificate reputation** - Enroll in Google Play App Signing for maximum trust.
- **Distribution channel** - Distribute via Play Store (even closed beta) for Google scanning.

### What Cannot Be Fixed (Without Feature Removal)

- **Sensitive permissions** - Required for core app functionality. Removing READ_SMS, READ_CALL_LOG, BIND_NOTIFICATION_LISTENER_SERVICE would eliminate the Communication AI feature entirely.
- **Sideload reputation for beta testers** - Until Play Store distribution is available, sideloaded APKs will always have lower trust.

### Recommendations

1. **Immediate:** Use the fixed signing pipeline with a production keystore (not debug, not test)
2. **Short-term:** Submit to Google Play Console for internal/closed testing track
3. **Medium-term:** Enroll in Play App Signing and establish certificate reputation
4. **Long-term:** Consider gating sensitive permissions behind user opt-in flows that are clearly documented in the Play Store listing

## 5. Security Recommendations

1. **Generate a dedicated production keystore** with strong credentials (see docs/android-release-signing.md)
2. **Store keystore securely** - only as GitHub Actions secrets, never in version control
3. **Enable ProGuard/R8** for production builds (currently disabled for beta) to make reverse engineering harder
4. **Implement certificate pinning** for API communication to prevent MITM attacks
5. **Add network security configuration** to restrict cleartext traffic
6. **Consider split APKs** or Android App Bundle to reduce APK size (currently 53.2 MB)
7. **Implement runtime permission requests** with clear explanations for each dangerous permission
8. **Submit Privacy Policy** addressing all sensitive data access (required for Play Store)
